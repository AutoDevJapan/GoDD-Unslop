# 日本語を最初の下書きから自然に書く

このSkillを読み込んだAI自身が、最初の下書きから本文を書く。このSkillのために追加のモデル呼び出しは行わず、別のAIや `godd-unslop rewrite` を通常の手順として呼び出さない。rewriteから呼び出された場合も再実行しない。モデルの重みを変更する仕組みではなく、日本語の品質を常に保証するものでもない。

## 書く前に

依頼の目的、読者、伝える結論、元資料で確認できる事実を押さえる。数値・単位・固有名詞・主語と責任主体・否定・条件・推測の強さ・期限・約束を保持する。曖昧な事実を自然さのために補わない。敬語を増やすことやくだけた語尾に変えることを品質の尺度にしない。引用、コード、URL、Markdownの構造は壊さない。

## 文脈を調べてから書く

背景が分からないまま書き始めず、使える手段で調べてから書く。

1. 利用者の依頼、会話、渡された資料、既存の報告テンプレート、利用者が示した組織の文体の資料を先に読む。
2. 利用者が明示した範囲の資料だけを調べる。会社や顧客の資料は、利用者がその利用を求めた範囲に限り、無関係な顧客や他社の資料は探さない。
3. 文書の目的、読み手、種類、会社の文体、参考例のうち、本文の書き方を左右する背景が残る場合だけ、具体的に質問する。調べれば分かることを聞かない。
4. 分からない背景を、想像で作らない。質問が必要でも、答えを待つだけで止めず、確定できる部分の下書きは進めて、未確定の前提を示す。

`godd-unslop rewrite` は別プロセスでツールなしに動くため、背景を自分で調べない。このSkillを使うAIが調べて整えた `context` を渡す。会社固有の文体が必須（`company_style_required` が true）なのに文体も参考例もない場合や、必要な事実が足りない（`missing_facts`）場合は、`needs_context` と質問を返し、想像で補わない。それ以外の正式な文書は、一般的な改まった文体で書ける。
## 下書きを組み立てる

- 読者が知りたい結論から具体的に書く。抽象語や名詞を積むより、誰が何をするかを動詞で示す。
- 理由と判断、条件と結果、行動と目的など、意味がつながる節を一文の中で自然につなぐ。一文に異なる話題を詰め込まない。
- 褒め言葉、不要な前置き、同じ結論の言い換え、架空の対立を加えない。専門語が読者の判断に必要なら具体的な説明とともに残す。

例（いずれも架空）:

修正前: 「確認を実施しました。結果は問題なしです。公開作業への移行が可能な状態です。」
修正後: 「確認で問題が見つからなかったため、公開作業へ進めます。」
理由と次の行動をつなぐ。実際に公開したとは書かない。

修正前: 「3回失敗した場合のみ停止します。成功時は停止しません。」
修正後: 「3回失敗した場合だけ停止し、成功時は停止しません。」
条件と否定をそのまま保つ。「3回」を「数回」に丸めない。

## 改行と空行

改行と空行は役割が違う。意味のまとまりと、まとまり同士の距離を、この二つで表す。

- 改行は、同じ話題の中で意味のまとまり（節や文）を読み分ける区切りとして使う。新しい要点、条件、補足、次の動作に移るところで入れてよい。
- 句点があるだけで必ず改行したり、必ず一文につないだりしない。前の文の理由・条件・結果として続けて読ませたい内容は一文につなぎ、独立した要点は文や行を分ける。
- 空行は、話題や段落が変わる距離を表す。同じ話題の中の行ごとに空行を入れず、別の話題の間には空行を残す。
- 原文に意図した改行や空行があれば尊重し、必要もなく一つにまとめたり詰めたりしない。原文に空行がなければ、必要がない限り空行を足さない。
- 箇条書き、手順、宛名、署名など、行の構造そのものに意味があるものは保つ。
- 文の長さ、段落数、文ごとの改行数を固定しない。短くまとめることを目的にしない。

例（いずれも架空）:

同じ話題の中で、つなぐ内容と分ける内容を区別する。

修正前:
```text
保存先を変更しました。次回から新しいフォルダーへ保存します。既存のファイルは移動していません。
```
修正後:
```text
保存先を変更したので、次回から新しいフォルダーへ保存します。
既存のファイルは移動していません。
```
変更と次回の動作はつなぎ、独立した補足は改行で分ける。

話題の切れ目の空行と、同じ話題の中の改行を両方残す。

修正前:
```text
確認は終わりました。
結果に問題はありません。

次の案件を説明します。
担当者は火曜日までに資料を用意します。
```
修正後:
```text
確認は終わり、結果に問題はありません。

次の案件を説明します。
担当者は火曜日までに資料を用意します。
```
空行は話題の距離、行の区切りは同じ話題の中の区切りとして残す。

原文で分かれている独立した案内を一つにまとめない。

修正前:
```text
料金は変わりません。

解約は設定画面から行えます。

不明な点は問い合わせ窓口へ連絡してください。
```
修正後:
```text
料金は変わりません。

解約は設定画面から行えます。

不明な点があれば、問い合わせ窓口へ連絡してください。
```
三つの案内は話題が別なので段落を保つ。語句を整えても、段落数を減らさない。

## 話題・視点・時制・確かさ・気持ち

原文と文脈から読み取れる範囲で、次の点を日本語として自然に整える。これらは置き換えの規則ではなく、文脈が支える場合だけ使う。支えがなければ、原文の言い切りの強さと人物の関係をそのまま保つ。

- 話題: 文で取り上げ直したい対象は「〜については」「〜は」で示せる。前後から主題が明らかなら付けない。すべての文に「については」を付けない。
- 行為と結果: 確認や調査をしたという行為と、その結果の判断は分けて書ける。原文に行為や根拠がなければ「確認した」と補わない。
- 状態・完了・予定: 「〜している」は継続や結果の状態、「〜である」は性質や断定、「〜した」は完了を表す。原文の状態・完了・予定を読み取り、予定を完了に、完了を予定に変えない。
- 視点と授受: 「〜してくれる」「〜していただく」は、その行為が話し手側の利益や依頼につながる関係が文脈で分かる場合だけ使う。関係が分からなければ「〜する」のまま保つ。
- 確かさ: 「予定です」「見込みです」「つもりです」「と思います」は確かさが違う。強めて約束にも、弱めて責任逃れにもしない。
- 願望と気持ち: 「〜したかった」「〜したい」「残念です」などは、原文や与えられた文脈にある場合だけ保つ。背景にありそうな感情を補わない。感情語を足して丁寧さや誠実さを演出しない。
- 他言語の文章: 語順や主語の省略が日本語では不自然になることがある。主語・視点・時制は、原文が示す範囲で日本語に合わせる。原文にない感情や関係は補わない。

呼び出し側が読み手、場面、伝えたい立場（audience, situation, stance）を渡した場合は、その範囲で上の判断を行う。渡されていない情報を聞き返さず、分かる範囲で書く。

例（いずれも架空）:

話題を取り上げ直す。

文脈: 保存先の変更を説明していて、ほかの設定にも触れている。
修正前: 「既存のファイルは移動していません。」
修正後: 「既存のファイルについては、移動していません。」
複数の話題のなかで対象を取り上げ直す例。前後から主題が明らかなら「は」のままでよい。

確認という行為と結果の判断を分ける。

修正前: 「確認は終わり、結果に問題はありません。」
修正後: 「確認した結果、問題ないことを確認できました。」
原文に確認を行ったことが書かれている場合の例。行為が書かれていない原文には使わない。

予定と視点を文脈が支える場合だけ表す。

文脈: 担当者は社内の同僚で、話し手の会議のために資料を用意する。資料はまだ届いていない。
修正前: 「次の案件を説明します。担当者は火曜日までに資料を用意します。」
修正後: 「次の案件については、担当者が資料を火曜日までに用意してくれる予定です。」
未完了の予定であり、話し手側のための行為だと文脈が示す例。

同じ原文でも、文脈がなければ足さない。

修正前: 「担当者は火曜日までに資料を用意します。」
修正後: 「担当者は火曜日までに資料を用意します。」
予定か約束か、誰のための行為かが分からないので、「予定」や「してくれる」を足さない。

感情は与えられた範囲だけ保つ。

修正前: 「返信が遅れました。」
修正後: 「返信が遅くなりました。」
お詫びを求める文脈や原文の表現がなければ、「大変申し訳ありません」などの感情語を足さない。

## 場面に合う文体

文体は場面と利用者の依頼に合わせる。敬語を増やすことも減らすことも、それだけでは品質にならない。

- 文体の指定がなければ、原文の文体を保つ。
- 社内の連絡や途中経過は、普段の話し言葉に近い文体でもよい場合がある。ため口の原文を、依頼なしにです・ます調へ直さない。
- 会社や取引先に出す報告資料、提案書などは、改まった文体で書く。その会社や組織の文体の特徴や参考例が与えられていれば、それに従う。与えられていなければ、一般的な改まった文体にとどめ、特定の会社らしさを想像で作らない。
- 文体を変えても、事実・数値・主体・約束・確かさは同じに保つ。くだけた文体から改まった文体へ直すときに、約束を強めたり、予定を確定にしたりしない。
- 参考例は文体を知るための見本として使う。例にある事実、名前、数値を本文へ持ち込まない。

同じ事実を場面で書き分ける例（いずれも架空）:

事実: 売上の集計は今日終わった。数値の確認は明日行う。

社内の気軽な連絡:
```text
集計は今日終わったよ。数字の確認は明日やるね。
```
社外へ出す報告資料。組織の文体は、です・ます調で、結論を先に置き、「いたしました」を使うとする:
```text
売上の集計は本日完了いたしました。数値の確認は明日実施いたします。
```
事実と、確認が明日であるという約束は同じに保ち、「予定」などの確かさを足さない。

## 宛先と調子

宛先、親しさ、チャンネル、調子が与えられた場合は、受け手が読んでどう受け止めるかを考えて、書き方を整える。与えられていない関係や好みは、立場や年齢から決めつけない。

- 部下へは、押し付けない、やわらかい調子にできる。くだけた言葉でもよいが、依頼や期限を曖昧にしない。
- 同僚へは、親しさに応じて、丁寧にもくだけた調子にもできる。
- 上司へは、関係に応じて、改まった丁寧さにも、親しみのある丁寧な調子にもできる。
- 社外の相手へは、関係が分からなければ丁寧に書く。
- 相手の気持ちを決めつけず、本人が伝えた好みや確認済みのやり取りを手がかりにする。職位から性格や感情を推測しない。
- 丁寧さを上げるために敬語を重ね過ぎない。「お送りいただけますでしょうか」より「お送りいただけますか」など、その場面に合う簡潔な依頼を選ぶ。提出先が明示した書式・用例があれば、それに合わせる。
- 関係性DBを使う場合は、今回の相手を指定して設定を読む。相手の一覧を自動収集したり、全員分の設定を一度にモデルへ渡したりしない。保存した相手が未確認なら、まず本人に内容を確認する。
- 呼びかけや敬称は、address に与えられたものだけを使う。名前や呼び方を想像で作らない。
- tone の formality（改まり）、warmth（温かさ）、directness（率直さ）は 0 から 4 の目安で、数が大きいほど改まる、温かい、率直になる。事実・数値・約束・確かさは、この値で変えない。
- 絵文字は、tone の emoji が light か match で、register が formal でなく channel が official でない場合だけ使える。light は原文より多くても2個まで、match は参考例か原文の絵文字の多さを超えない。改まった文書（register が formal）と公式文書（channel が official）では使わず、原文にある飾りの絵文字も取り除く。引用やコードの中の絵文字は変えず、使ってよいか質問する。tone と register や channel が食い違うときは、改まった側を優先する。謝罪・注意・深刻な報告では、許可されていても使わない。
- 調子を変えても、感情や関係を足さない。温かさは、与えられた事実と依頼の範囲で、言葉づかいに表す。

例（いずれも架空）:

事実: 明日の会議の資料を、確認しておいてほしい。

親しい部下へのチャット（warmth 3、emoji light）:
```text
明日の会議の資料、確認しておいてもらえると助かるよ。よろしくね🙂
```
上司へのメール（改まった丁寧さ）:
```text
明日の会議の資料について、ご確認をお願いいたします。
```
公式文書:
```text
明日の会議の資料について、確認をお願いします。
```
どれも確認してほしい内容は同じで、公式文書には絵文字を使わない。

## 出力前に

原文や資料と照合し、情報を落としていないか、条件や主体が移っていないかを読む。言い換えただけで意味の一致を保証しない。本文を求められたら完成した本文を返し、推敲の説明だけで終えない。

利用可能なら `godd-unslop analyze` で表現候補、`compare` で原文と改稿を照合できる。候補は採否を判断するための補助であり、全件の機械的修正はしない。数字や否定語の件数が同じでも意味が同じとは限らない。

明示された修正例だけを `style-learn` へ渡せる。返るJSON設定を利用者が明示的に保存し、`style-review` へ渡す。自動で会話履歴や私的な文例を集めたり、公開したりしない。学習は前後の文字列との一致に基づき、意味解析や口調の推定ではない。設定内の競合は勝手に一方を選ばない。ツールがない環境でも、このSkillの方針で本文を書き、使っていないツールを実行済みと言わない。
